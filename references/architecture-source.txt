                              Executive summary
 OmniRoute should be built as a conversation operating layer, not as three chat windows placed beside
 one another. The platform owns the canonical history, files, memory, branches, cost records, and
 permissions. GPT, Claude, Gemini, and future providers are replaceable execution engines behind a
 stable provider interface.

    Your conversation stays. Your AI can change. The defensible value is cross-model continuity,
    response comparison, capability-aware switching, reliable usage accounting, and a growing

 1. Product definition and boundaries
 What OmniRoute is, what it is not, and why the distinction matters.

 OmniRoute is a unified multi-model workspace. A user sends one prompt to a chosen set of providers,
 views each response in a coherent comparison interface, selects the preferred answer, and continues
 the conversation with that provider. At any later point the user can switch providers; OmniRoute
 reconstructs the relevant shared context so the new provider starts from the current state instead of
 from zero.

 The platform is therefore responsible for four kinds of continuity:

   - Conversation continuity: the active branch, selected responses, recent turns, summaries, and pinned
     instructions.

   - Artifact continuity: uploaded files, generated code, images, citations, and reusable outputs.

   - Economic continuity: reservations, token usage, credits, refunds, and provider-specific cost records.

   - Experience continuity: a stable composer, history, keyboard behavior, streaming pattern, and error
     model across providers.

    Avoid the weak pitch
    Do not present the product as an 'AI API aggregator.' Present it as a cross-model conversation
    workspace that removes the manual copying, re-uploading, and re-explaining users perform
    today.

 2. User experience blueprint
 The interface should feel like one capable workspace, not three products stitched
 together.

 The user should make only two major decisions: how many AIs to ask and which answer to continue
 with. Provider mechanics, API differences, retries, token accounting, and context conversion stay

 A switch does not copy every historical candidate. The context engine follows the active selected path,
 adds pinned memory, current artifacts, a conversation summary, relevant older turns, and the latest
 user request. Rejected alternatives stay stored but are excluded unless the user references them.


 3.3 Provider limit or outage

    Recommended recovery copy

    selected context and files will stay attached.' The system should not claim zero context loss; it
    should promise transfer of the relevant saved context.

 4. System architecture
 Start as a modular monolith with independent provider adapters and operational
 boundaries.



                                           Next.js Web App




                                         NestJS API Gateway


      PostgreSQL                                                                     Object Storage

                                        Conversation + Context
                                               Engine

    Redis + Queue                                                                      Telemetry


                                         Provider Orchestrator




                       OpenAI Adapter      Anthropic Adapter        Gemini Adapter




 The diagram separates ownership of state from execution of inference. PostgreSQL is the system of
 record. Redis accelerates ephemeral coordination but is never the only copy of a credit transaction or
 selected branch. Object storage holds large files and artifacts. The provider orchestrator fans out model
 calls and emits normalized events.


 4.1 Why a modular monolith first
   - One deployable backend is easier to debug, test, observe, and afford during an MVP.

   - NestJS modules still create boundaries around identity, conversations, context, providers, usage,
     files, and analytics.

   - Heavy or unreliable work moves to background workers without requiring a premature microservice
     program.

   - Services can be extracted later from measured bottlenecks, not imagined scale.

    Do not start with
    Kubernetes, Kafka, event sourcing, a separate vector database, a service mesh, or an ML
    router. Each adds operational work without improving the first comparison-and-switch loop.

 5. Provider abstraction and orchestration
 Normalize the common core without pretending every provider is identical.

 Each adapter accepts a canonical request and emits canonical events. Provider-specific features remain
 available through capability flags and typed extension fields. This avoids a
 lowest-common-denominator interface while keeping the rest of the application independent from SDK
 churn.

     interface AIProvider {
       id: ProviderId;
       capabilities(): Promise<CapabilitySnapshot>;
       streamChat(request: CanonicalChatRequest): AsyncIterable<ProviderEvent>;
       cancel(runId: string): Promise<void>;
       estimate(request: CanonicalChatRequest): Promise<UsageEstimate>;
     }

     type ProviderEvent =
       | { type: 'run.started'; providerRequestId?: string }
       | { type: 'content.delta'; text: string }
       | { type: 'tool.call'; call: CanonicalToolCall }
       | { type: 'usage.updated'; inputTokens?: number; outputTokens?: number }
       | { type: 'run.completed'; usage: NormalizedUsage }
       | { type: 'run.failed'; error: NormalizedProviderError };




 5.1 Parallel comparison orchestration
   1. Validate user, workspace, provider selections, file permissions, and quota.

   2. Create an idempotent request group, a user turn, and one pending model run per provider.

   3. Reserve the maximum allowed credits transactionally before calling external APIs.

   4. Start adapters concurrently with per-provider timeouts and independent cancellation tokens.

   5. Multiplex normalized events over a single SSE connection using run IDs and monotonically
      increasing event IDs.

   6. Persist final outputs and usage, reconcile reserved versus actual credits, and publish terminal
      states.

   7. Allow selection after one response completes; do not require the slowest provider to finish.

 6. Conversation branching and shared context
 The active conversation is a path through a tree, not a flat provider-owned thread.



                                                         User prompt




                                                       Claude response
               GPT response                                                                        Gemini response
                                                           selected




                                                        Next user turn




 For each user turn, OmniRoute may store multiple model responses. One response becomes active. The
 next user turn points to that selected response, which makes the branch explicit and reversible. If the
 user later chooses another candidate from an earlier turn, the application creates or activates a
 different path rather than rewriting history.


 6.1 Context assembly algorithm
   1. Resolve the active branch from the current conversation head back to the root.

   2. Collect system instructions, workspace rules, pinned user memory, and current task metadata.

   3. Attach the latest turns verbatim within a fixed recent-history budget.

   4. Retrieve older relevant turns, file chunks, and artifacts using lexical search first and embeddings
      when justified.

   5. Add a versioned conversation summary that records decisions, constraints, open tasks, and artifact
      references.

   6. Convert canonical messages and tools into the target provider's current request format.

   7. Record a context snapshot hash, token estimate, included source IDs, and summary version for
      auditability.

 7.1 Credit ledger, not a mutable counter
      BEGIN;
        SELECT available_credits FROM credit_wallets
        WHERE user_id = $1 FOR UPDATE;

           INSERT INTO credit_transactions
             (user_id, request_group_id, amount, type, status)
           VALUES ($1, $2, -$3, 'RESERVATION', 'PENDING');

        UPDATE credit_wallets
        SET available_credits = available_credits - $3,
            reserved_credits = reserved_credits + $3
        WHERE user_id = $1;
      COMMIT;



 After provider completion, the system writes actual usage and reconciles the reservation. This prevents
 double spending across parallel requests, supports refunds, and gives support teams an auditable
 history. Money values use integer minor units or precise decimals; never binary floating point.

 7.2 Essential constraints and indexes
   - Unique idempotency key per user and logical request group.

   - At most one active selected response per turn, enforced transactionally.

   - Foreign keys from runs to turns and responses to runs; soft deletion only where retention policy
     requires it.

   - Indexes on conversation_id + created_at, turn_id + provider, user_id + created_at, and
     request_group_id.

   - JSONB only for provider-specific metadata and versioned capability snapshots, not for all relational
     state.

 9.1 Why PostgreSQL rather than MongoDB
 The core records contain strong relationships and money-like invariants: users own workspaces,
 conversations contain turns, turns contain multiple runs, one response becomes active, and usage
 reconciles against ledger transactions. PostgreSQL transactions, constraints, joins, JSONB, full-text
 search, and optional vector support handle this combination without introducing a second primary
 database.


 9.2 Why NestJS rather than only Next.js route handlers
 Next.js route handlers can ship a prototype, but OmniRoute's backend has provider adapters,
 background jobs, ledger transactions, context policies, file processing, retries, and observability. A
 separate NestJS application makes those responsibilities explicit and gives the project stronger backend
 engineering depth. Keep the web application focused on experience and the API focused on
 orchestration.

 12.1 Minimum production security checklist
   - HttpOnly, Secure, SameSite cookies; CSRF protection where needed; short session lifetime with
     rotation.

   - Schema validation at every API boundary and strict content-type and size checks.

   - Per-workspace authorization before database reads, file access, provider calls, and exports.

   - Audit events for login, file access, provider switch, tool execution, credit adjustment, export, and
     deletion.

   - Prompt and response content excluded from routine logs; use IDs, counts, hashes, and redacted
     metadata.

   - Threat model reviewed against OWASP risks including prompt injection, sensitive disclosure,
     improper output handling, excessive agency, and unbounded consumption.

    Tool execution boundary
    The model proposes a tool call; OmniRoute validates the schema, authorization, scope, and
    required user approval; the application executes it; the result returns to the model. Never
    grant a model direct database or cloud credentials.

 16.3 Commercial and strategic assessment
 The concept is attractive as a productivity product and excellent as a resume project. As a standalone
 horizontal startup, however, 'access many models' is not enough. The strongest strategic path is to own
 the workflow and state around model use: projects, branches, files, reusable instructions, team
 approvals, evaluations, and provider-independent audit history.

   Question                   Assessment

   Is there a real problem?   Yes. Users manually move prompts, files, and context across tools when a
                              model fails or another capability is needed.

   Is the MVP feasible?       Yes. Three provider adapters, parallel streaming, branching, context handoff,
                              credits, and history are achievable with disciplined scope.

   Is it cheap to operate?    No. Compare mode multiplies inference calls, so quotas, pricing, caching, and
                              output controls are core product design.

   Is it defensible today?    Only moderately. Defensibility grows from workflow depth, team adoption,
                              evaluation data, and domain specialization.

   Best initial positioning   A developer and technical-learning workspace for comparing solutions and
                              continuing across models.

   Go / no-go                 Go for portfolio and closed-beta validation. Do not scale free credits or
                              infrastructure before measuring retention and willingness to pay.



    Best business model sequence
    Begin with limited free platform credits and a paid usage tier. Add team workspaces and
    administrative controls before complicated autonomous agents. Consider BYOK only after the
    core experience is trusted and secure.




 17. Final recommendation
 Build the conversation layer first and let model intelligence remain replaceable.

 OmniRoute should launch around one polished loop: ask three, choose one, continue, and switch
 without re-explaining. Everything in the architecture should protect that loop. The frontend makes
 comparison calm and switching obvious. The conversation engine owns the active branch. The context
 engine transfers relevant state. Provider adapters absorb API differences. PostgreSQL protects history
 and credits. Redis coordinates short-lived work. Observability connects user experience, reliability, and
 cost.

 The product becomes weaker when it attempts every provider feature, autonomous routing, and
 infrastructure pattern at once. It becomes stronger when it is transparent about costs, explicit about
 provider boundaries, careful with privacy, and excellent at preserving work across provider changes.
